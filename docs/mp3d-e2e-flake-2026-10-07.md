# mp3d canvas-ready e2e flake — 2026-10-07

## Summary

Full Chromium e2e on tip `cursor/integration-fold-wave4-tip-36e4` (PR #476) hit **13**
`waitForMp3dReady` / `canvas[data-mp3d-ready="1"]` timeouts under software GL
(SwiftShader / ANGLE) on CI-like VMs. Tests were not skipped; readiness + wait
posture were fixed so the ready signal is reliable and the wait is software-GL-aware.

## Before / after

| Metric | Before | After |
| --- | --- | --- |
| Unique mp3d flag-on specs failing on `canvas-ready` | **13** (FIAR×2, Hex×2, Kings×1, Kwatro×1, Pent×2, Prime×2, Queens×1, Star Track×2) | **0** |
| `waitForMp3dReady` default timeout | 30s flat | **60s in CI** / 45s locally |
| Ready signal | Sync `paint()` only; throw → never marked | `paintBoard3dAndMarkReady` + double-rAF mount paint + rAF retry |
| WebGL failure visibility | Silent 2D fallback; e2e waited 30s on a missing canvas | Host sets `data-mp3d-fallback`; wait fails fast with reason |
| Chromium launch | Playwright defaults only | Explicit SwiftShader ANGLE args |

## Root cause

Ranked:

1. **Silent WebGL → 2D fallback** — Controllers catch `WebGLRenderer` failures /
   context loss and keep the classic 2D SVG/DOM board. Playwright then waited for
   `canvas[data-mp3d="…"][data-mp3d-ready="1"]`, which **never appears**. Error
   contexts from CI showed 2D a11y (`valid placement` SVG cells) with no canvas.
2. **Software GL first-frame fragility** — Under SwiftShader, the first
   `renderer.render` can throw or run before layout settles. Ready was only set
   after a successful sync paint, so a transient first-frame failure left the
   attribute unset until a later update (sometimes never within the wait).
3. **Timeout too tight for CI software GL** — 30s was enough on warm local runs
   but not a safe budget when Three.js chunk load + context create + first paint
   contend on ubuntu CI VMs.
4. **Chrome SwiftShader opt-in** — Chrome 127+ needs `--enable-unsafe-swiftshader`
   (and ANGLE SwiftShader) for reliable WebGL on headless CI; without a working
   context the boards fall into (1).

Not a gameplay / AI / scoring bug.

## Fix

### App (`src/ui/three/tablet-gl.ts` + eight `*-board-3d.ts`)

- `paintBoard3dAndMarkReady` — try/catch paint, mark `data-mp3d-ready="1"`, one
  rAF retry on throw.
- `scheduleBoard3dMountPaint` — double-rAF after mount/resize so layout settles
  under software GL before the readiness paint.
- `markBoard3dWebGlFallback` / `clearBoard3dWebGlFallback` — host
  `data-mp3d-fallback` for e2e diagnostics.

### Controllers (eight board3d games)

- On WebGL catch / permanent context-loss fallback: set `data-mp3d-fallback`.
- On successful mount: clear the attribute.
- No rules, scoring, or AI behavior changes.

### Playwright

- Chromium project `launchOptions.args`: `--use-gl=angle`,
  `--use-angle=swiftshader-webgl`, `--enable-unsafe-swiftshader`.
- `waitForMp3dReady`: CI 60s; wait for ready **or** fail fast on fallback;
  then assert attached + visible.
